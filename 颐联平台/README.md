# 颐联 · 多角色生活协同平台(演示)

面向居家养老场景的三端协同原型:**老人端**(自主安排生活)、**家属端**(在授权范围内协助)、**社区端**(服务调度)。三个角色各有独立界面与权限视角,通过同一件事在不同端之间的流转来演示"协同"。

---

## ⚠️ 先读这一段:哪些是真的

| 事项 | 现状 |
| --- | --- |
| 后端 / 接口 | **有**,但只服务「邮箱登录 / 邮箱关联 / 老人给家属发消息」(`server.py`,仅用 Python 标准库) |
| 登录方式 | **真实**:邮箱 + 6 位验证码,通过 QQ SMTP 发出 |
| 关联规则 | **真实,服务端校验**:老人最多绑 5 位家属,家属最多关联 5 位老人;老人至少绑 1 位才能发消息 |
| 其余角色数据 | 仍是浏览器 `localStorage`(事项、授权、社区队列、核验记录等) |
| 权限隔离 | 登录与发信有服务端校验;角色页面的"只读"仍只是界面约定 |
| 外部依赖 | 发信依赖 `smtp.qq.com`;字体走系统字体栈 |

**登录、绑定、邮箱消息是真的**(服务端 + SQLite + SMTP);三端里的事项、授权、队列、核验记录仍然是本机演示数据。

因此「按需授权」「全程留痕」仍属于**产品能力的示意**:

- 三个角色共用同一个 origin 的 `localStorage`,在开发者工具里改 `yilian-permissions` 就能绕过授权;
- `yilian-contact-requests` 之类的"留痕"是普通数组,可以随意改写,不构成审计证据。

**真正上线还需要**:服务端鉴权贯穿全部数据、按角色的服务端权限校验、不可篡改的审计日志、数据加密与最小化下发、验证码防刷与风控。当前原型适合作为交互与信息结构的提案,不宜直接承载真实老人数据。

## 运行

需要 Python 3.9+。**不要**再用 `python -m http.server` —— 登录与发信要走 `server.py`:

```bash
python server.py
```

端口默认 8000,可用环境变量覆盖(如 `PORT=3000 python server.py`)。

首次运行前,把 `.env.example` 复制为 `.env` 并填写邮箱与**授权码**(不是登录密码):

```
MAIL_SERVER=smtp.qq.com
MAIL_PORT=587
MAIL_USE_TLS=true
MAIL_USE_SSL=false
MAIL_USERNAME=你的邮箱@qq.com
MAIL_PASSWORD=邮箱授权码
MAIL_DEFAULT_SENDER=你的邮箱@qq.com
```

`.env` 与 `data.db` 已在 `.gitignore` 中。**SMTP 凭据只在服务端读取,不会下发到浏览器**;浏览器只保存一个随机 session token。

打开 http://localhost:8000/ :

1. 首屏点居中的「登录」;
2. 在下一屏选一个入口:**老人端 / 家属端 / 社区端**;
3. 老人端、家属端需要**邮箱 + 验证码**登录(社区端是工作人员,直接进);
4. 登录成功后**先绑定对方邮箱**(还没绑过时),点「绑定并进入」才进内部页面;
5. 进入角色页后**第一次会弹出「设置头像与昵称」**,保存后开始使用。

角色页右上角有「退出」,入口页右上角也有「退出登录」;未登录直接访问 `/elder/` 或 `/family/` 会被送回入口页。

登录后在入口页右上角「我的账户」里管理邮箱关联:添加对方邮箱(老人加家属、家属加老人,各自上限 5)。

**只有一个邮箱的情况**:登录后的绑定步骤点「只有一个邮箱?用同一个邮箱」,就把这个邮箱同时作为老人和家属绑定。之后用同一个邮箱分别以两种身份登录(或在账户里切换身份),老人端和家属端看到的就是同一对关系。

老人至少绑定 1 位家属后,老人端「联系支持者」里的「给家属发消息」才会出现。

> 安全提醒:邮箱授权码等同于密码。如果它出现在聊天、截图或提交记录里,请到 QQ 邮箱「设置 → 账户」重新生成一个新的授权码。

seed.js               演示种子数据(唯一的数据来源)
shared.js             三端共用的工具层:存储读写、日期、视图路由、抽屉、提示

### 三端各自能做什么

- **老人端** `/elder/` — 查看今天最重要的事并**确认社区陪诊**;管理生活事项(新建/查看进度);主动联系支持者并接收回复;开关共享授权;把可疑短信、链接或电话号码粘进「安全核验」做本地分析,查看自己的核验记录,并把某个号码标成"可信"。
- **家属端** `/family/` — 查看老人的出行确认状态、回复老人的联系请求、查看**已授权**的共享事项、在授权范围内查看**老人的安全核验记录**、只读查看授权范围、查看协同记录。**不能替老人确认**——出行方式只能由老人本人在老人端确认。
- **社区端** `/community/` — 按风险/时限处理协同队列、承接事项、查看 8 位值班人员的资源与负荷、配置调度规则;数字安全专员可用「安全核验」协助居民核验可疑信息,并把高风险一键转成协同事项。可在左下角切换"当前登录的服务人员",每个人的工作台与待办是独立的。

### 入口页:滚动驱动的视频主视觉

入口页(`/`)用一段 6 秒的视频做背景,但**不是自动播放,而是由滚动驱动**:

1. 加载时把视频取成 blob,逐帧 seek 抽出 24–72 张图(宽 480–720px);
2. 滚动进度映射为帧序号,画到铺满视口的 canvas 上 —— 滚动即播放;
3. 一层很淡的粒子缓慢漂移;
4. 滚到第二屏时,三条协同原则淡入。

**为什么抽帧而不是直接播视频**:抽帧不依赖自动播放,后台标签页、静音自动播放被拦截、低端机上都能稳定出画面;而且滚动随时可能停下,直接 seek 视频会卡顿。

**降级路径**
- ≤800px:只抽 40 帧、宽 480,不画粒子;
- 系统开启"减少动态效果":只显示一帧静止画面,不做抽帧/粒子/滚动联动;
- 抽帧失败:退回让 `video.currentTime` 跟随滚动;再失败则保留暖色渐变底。

视频源是外部的(约 6.3 MB)。要换成本地素材,改 `index.html` 里 `#heroVideo` 的 `data-src` 即可。

## 数据与存储键

所有状态都在 `localStorage`。键名集中定义在 `shared.js` 的 `KEYS` 里:

| 键 | 内容 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| `yilian-events` | 老人的生活事项 | 老人端 | 老人端、家属端(按授权过滤) |
| `yilian-contact-requests` | 老人发出的联系请求与回复 | 老人端(发起)、家属端(回复) | 老人端、家属端 |
| `yilian-permissions` | 共享授权四个开关 | 老人端 | 老人端、家属端 |
| `yilian-escort` | 「确认社区陪诊」的状态 | 老人端 | **三端共读** |
| `yilian-community-queue` | 社区协同队列(含承接结果) | 社区端 | 社区端 |
| `yilian-community-rules` | 调度规则开关 | 社区端 | 社区端 |
| `yilian-risk-checks` | 安全核验记录(风控留痕) | 老人端、社区端 | 老人端、家属端(按授权)、社区端 |
| `yilian-trusted-numbers` | 可信号码名单 | 老人端(可在核验结果里添加) | 三端共用 |
| `yilian-trusted-domains` | 可信域名名单 | 种子数据 | 三端共用 |
| `yilian-large-text` | 大字模式 | 三端 | 三端 |
| `ylCommunityStaff` | 社区端当前登录人员 | 社区端 | 社区端 |

页面之间靠 `storage` 事件同步(该事件只在**其他**标签页触发,所以单开一个标签页时看不到"另一边"的变化)。

### 三端是怎么串起来的

1. **复诊出行确认(主线)** — 老人端点「确认社区陪诊」→ 写入 `yilian-escort` → 家属端的"需要协助"从 1 变 0、卡片状态变成"老人已确认"、协同记录新增一条;社区端队列里 `周淑兰 · 确认陪诊安排` 的状态跟着变成"老人已确认"。
2. **联系消息** — 老人端发起联系请求 → 家属端"待回复"计数 +1 并可回复 → 老人端出现通知角标与对话记录。
3. **共享授权** — 老人端关掉某一项后,家属端"共享事项"里对应类型的事项立即消失;家属端始终只读。
4. **可疑信息核验(风控)** — 老人端把可疑短信、链接或号码粘进「安全核验」;判定为高风险或中等风险时,可以「发给女儿帮我看」或「发给社区专员」,把"风险结论 + 原文摘要"一键转出去,直接进入家属端的待回复收件箱。风控结果因此进入三端协同,而不是停在老人自己的屏幕上。
   - **可信名单参与判定**:同一条内容,来自可信号码(家人、社区、官方)还是陌生号码,得分不同 —— 这是"发信人是谁"的轻量实现。老人可以在核验结果里把某个号码标成"可信"。
   - **留痕**:每次核验写入 `yilian-risk-checks`,老人端有「最近的核验记录」;家属端只有在「数字安全核验」这项授权打开时才能看到,授权一关立即清空。
   - **社区端**:数字安全专员有独立的核验入口,高风险可以一键生成一条协同事项进入「协同队列」跟进 —— 风控和调度在这里闭环。

### 邮箱登录与关联(真实后端)

| 规则 | 值 |
| --- | --- |
| 登录 | 邮箱 + 6 位验证码;10 分钟有效;60 秒后可重发;1 小时最多 5 次 |
| 验证码尝试 | 最多 5 次,超出需重新获取 |
| 老人 ↔ 家属 | 一位老人最多绑 5 位家属;一位家属最多关联 5 位老人 |
| 同一个邮箱 | 支持:一个邮箱可同时作为老人和家属(兜底方案),身份在登录时选择 |
| 发送前提 | 老人至少绑 1 位家属;只能发给已绑定的邮箱(服务端 403 拦截) |

接口(JSON,登录后带 `Authorization: Bearer <token>`):

```
POST /api/auth/request-code   发验证码
POST /api/auth/verify         验证码换 token
POST /api/auth/logout         退出
GET  /api/me                  当前账号与关联
POST /api/role                选择身份 elder / family
POST /api/bind                添加关联(校验双向上限)
POST /api/unbind              解除关联
POST /api/messages            老人发给已绑定家属
GET  /api/messages            收件箱
```

**每位用户的数据是自己的**

- 登录后**进入老人端/家属端时**才会弹出「设置头像与昵称」(入口页和管理后台不弹),头像可以选默认字符,也可以上传照片(前端自动裁成 160×160);
- 老人的事项、共享授权、联系消息按邮箱分区存在 `localStorage`(`yilian-events:<邮箱>` 等),互不混用;
- 家属端看到的是**已绑定老人**的事项与确认状态(按老人自己的授权过滤);
- 社区端「服务资源 → 服务对象名单」列出所有选择过身份的用户,每登录一位就多一个名字,刷新可见。

### 网站主管:管理后台

在 `.env` 里配置管理员邮箱,分两级(都可多个,逗号分隔):

```
ADMIN_PRIMARY_EMAILS=xjxsbaby0926@gmail.com     # 主管:全部权限,含删除账号
ADMIN_SECONDARY_EMAILS=2116164179@qq.com       # 副管:查看用户、重置用户,不能删除
```

用上述邮箱登录后访问 **`/admin/`**(入口页右上角一直有「管理后台」链接,登录后「我的账户」里也会出现):

- 查看全部账号:昵称、邮箱、角色、关联数、消息数、注册时间,并标出谁是主管/副管;
- **重置为新用户** —— 清空昵称、头像、关联、消息与会话,对方下次登录会重新要求设置资料(主管与副管都可以);
- **删除** —— 连账号一起删除(只有主管可以;副管页面不显示这个按钮,接口也会返回 403);
- 管理员之间也有边界:不能操作自己的账号;副管不能动其他管理员;主管账号不可被删除。

两个危险操作都要点两次确认。接口同样在服务端校验:`GET /api/admin/users`、`POST /api/admin/reset`、`POST /api/admin/delete`;未登录返回 401,非管理员邮箱返回 403。旧的 `ADMIN_EMAILS` 仍兼容,按主管处理。

数据库 `data.db` 里是 `users / codes / sessions / bindings / messages` 五张表,会话 token 是 32 字节随机串;验证码与 token 都不写进前端代码。

## 资源与缓存

静态资源统一带一个版本号,四个 HTML 里的值**必须保持一致**:

```html
<link rel="stylesheet" href="../role.css?v=8"/>
<script src="../seed.js?v=8"></script>
```

**改动任意 `.css` / `.js` 后,请把所有 `?v=8` 一起改成 `?v=9`(再下次改 v=10),否则浏览器可能继续用缓存里的旧文件。** 项目没有构建步骤;如果后续接入了打包工具,这一步可以交给工具生成内容哈希。

## 样式结构:`role.css` 的 @layer

这个文件是历史上几次视觉迭代**叠加**出来的(初版 → 2026 视觉系统 → 玻璃拟态层 → 社区人员切换器)。原先"谁生效"取决于规则在文件里出现的先后顺序,很难维护;现在改为显式分层:

```css
@layer base, system2026, glass, staff, a11y, fixes, theme;
```

- `base` 初版结构(栅格、组件骨架、基础排版)
- `system2026` 2026 视觉系统(配色、圆角、动效基调)
- `glass` 玻璃拟态表面层(已被 `theme` 整体覆盖,保留仅作历史与降级参考)
- `staff` 社区端"当前登录人员"切换器
- `a11y` 无障碍与低端设备性能,以及本轮新增的界面元素
- `fixes` **例外层**:少数必须压过后面图层的高优先级规则,每条都写了原因
- `theme` **最终视觉主题「赭石纸本」**:暖纸底色、赭石与云杉、极细分隔线、方角、衬线标题

**新增样式请加进 `theme`;新增行为/无障碍规则加进 `a11y`;确实需要压过 `theme` 时再加新层并写明原因。** 分层之后,层与层之间的优先级由上面这行声明决定,同层内才看选择器权重和先后顺序——注意这与"不看分层、纯按权重"的直觉不同,`fixes` 里那几条例外正是为此存在。

字号统一用 `rem` 表达,所以「大字模式」只是把 `<html>` 的字号放大到 118%,整页文字随之变大(`html.large-text`)。

## 无障碍与低端设备

- **移动端抽屉**:≤800px 时侧边栏是抽屉。收起时通过 `inert` 移出 Tab 序与可访问性树(不支持 `inert` 的旧浏览器回退到 `visibility:hidden`);打开时焦点自动进入抽屉第一项,关闭(Esc / 点遮罩)后焦点回到菜单按钮。
- **导航语义**:当前栏目写入 `aria-current="page"`;视图切换会同步到地址栏 hash,可深链、可后退。
- **大字模式**:见上,按钮同时带 `aria-pressed`。
- **低端设备**:≤590px 会关闭大面积 `backdrop-filter` 与 `background-attachment:fixed`,并隐藏两个固定的模糊装饰圆点,避免老人机上滚动掉帧(玻璃质感会弱一些)。
- 已处理 `prefers-reduced-motion`。

## 已知的简化之处

- 「确认社区陪诊」等状态没有时间维度的日程模型,`明天上午 09:30` 是文案而非真实日程。
- 社区端的服务负荷按"名下事项数 / 能力上限"实时估算,不是真实排班系统。
- 事项与人员的数量都是演示用的样本规模(16 条队列、8 位值班人员)。
- 安全核验(`safety.js`)是**本地规则匹配**,分三个维度:① 话术(36 类,按诈骗阶段/类型组织)② 链接(仿冒品牌域名、可疑顶级域、短链、IP 直连、punycode、`@` 伪装)③ 号码(境外前缀、95/400 冒用、仿冒官方号、字母冒充数字);另有 9 条**组合信号**(跨类别共现,如"索要验证码 + 要求保密""谎称亲人出事 + 要求打钱""陌生号码 + 涉及资金")。判定还会参考**可信名单**(号码与域名):同一条内容来自可信号码还是陌生号码,得分不同。另外识别两种**结构信号**——中文数字金额("打十万""叁万元")和"把钱打过去/转过去"的索财句式,这两类写法在老人收到的短信里比阿拉伯数字常见得多。高风险/中等风险会给出**事后处置步骤**,并可把结论一键转给家属或社区。报告结构由 `YL_SAFETY.renderReport()` 统一生成,三端一致。
- 它不做语义理解,**判断不了语境**——例如「妈,你一个人住吗」会被标成低风险提示、而陌生人问同一句话配上"加个微信"才是高风险,因为分析器不知道发信人是谁。真实系统必须结合发信人身份(需要账号体系)才能进一步减少误报。要真正可用还得接反诈特征库、样本模型和人工复核,规则也需要能远程更新。
